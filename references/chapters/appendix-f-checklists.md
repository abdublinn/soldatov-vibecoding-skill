# Чек-листы

## Главная мысль

Чек-лист — это ворота между этапами, а не перечень пожеланий. Он защищает от типовых пропусков в повторяющейся работе и делает решение о переходе явным: готово, не готово или принято с известным риском. Сильный пункт наблюдаем и имеет доказательство; «проверить качество» слабее, чем «ключевой сценарий пройден в чистом окружении, ссылка на результат». Чек-лист не заменяет мышление и дополняется при обнаружении нового класса ошибки.

## Модели и правила

- Основные gates: **идея → требования → проектирование → генерация → локальная приёмка → изменение → deploy → эксплуатация → handoff**.
- Пункт формулируется как проверяемое состояние, а не действие. Рядом полезно указывать доказательство, владельца и исключение.
- Критические пункты блокируют переход: потеря данных, отсутствующая авторизация, непроверенный rollback, секреты, неработающий основной сценарий.
- `N/A` допустимо только с объяснением. Пустая галочка не означает согласованного исключения.
- Для маленького MVP чек-лист сокращается, но не удаляет безопасность, данные, запуск и приёмку.
- После инцидента добавляй пункт только если он предотвращает повторение и имеет дешёвую проверку; иначе чек-лист превращается в шум.

## Практический метод

Перед кодом проверь: пользователь/проблема/ценность названы; сценарий и границы MVP согласованы; данные, роли, статусы и acceptance описаны; архитектура и риски понятны; неизвестное вынесено в вопросы. Перед первым запуском: зависимости и env документированы; миграции понятны; секреты исключены; команда запуска известна. Перед commit: `status`, `diff`, тесты, отсутствие секретов/артефактов, одна логическая задача.

Перед изменением production зафиксируй версию, backup, scope, владельца, окно, health/smoke и rollback. После deploy проверь:

```bash
docker compose ps
docker compose logs app --tail=100
curl -f http://127.0.0.1:8000/health
```

Затем пройди внешний ключевой сценарий, сохранность данных, роли, ошибки, HTTPS и мониторинг. Перед handoff: README проверен в чистом окружении; доступы имеют owners; временные секреты ротированы; limitations/backlog/runbook переданы; приёмка зафиксирована. Храни чек-лист рядом с процессом и ссылками на evidence.

## Антипаттерны

- Один универсальный список на сотни пунктов без связи с риском и этапом.
- Пункты «всё протестировано», «безопасность проверена», «документация готова» без доказательств.
- Автоматически отмечать AI-сгенерированные пункты выполненными.
- Продолжать этап при провале критического gate, обещая «исправить потом».
- Использовать `N/A`, чтобы скрыть отсутствие владельца или понимания.
- Проверять только наличие файла/процесса, но не пользовательский результат.
- Не обновлять список после повторяющегося инцидента или держать устаревшие пункты навсегда.

## Критерии проверки

- Для каждого этапа есть короткий релевантный gate с критическими пунктами.
- Каждый пункт имеет бинарно наблюдаемое состояние и, где нужно, ссылку на evidence.
- Исключения `N/A` объяснены и приняты владельцем риска.
- Переход блокируется при отсутствии backup/rollback, утечке секрета или провале ключевого сценария.
- Команды действительно запущены в нужном окружении, а не перенесены из примера.
- Чек-лист отражает текущую архитектуру, инструменты и ответственность.
- После handoff новый владелец может повторить проверки без устных подсказок автора.
