# Деплой проекта: как довести приложение до сервера

## Главная мысль

Деплой — не команда запуска, а управляемый переход от проверенной версии к доступному пользователю сервису. Успех означает, что приложение работает в целевом окружении, открывается по нужному адресу, использует правильные секреты и постоянные данные, проходит внешний сценарий и может быть откатано. Статус `running` подтверждает только жизнь процесса, но не ценность продукта. Вайбкодер отвечает за всю цепочку: сервер, контейнеры, сеть, домен, HTTPS, данные, проверку и передачу эксплуатации.

## Модели и правила

- Контур релиза: **preflight → резервирование данных → доставка версии → запуск → внутренний health-check → внешний smoke-тест → наблюдение → фиксация версии**.
- До изменения зафиксируй текущую версию, состояние сервисов, способ отката и владельца доступа. Для данных отдельно определи backup/restore; копия кода не заменяет резервную копию БД.
- Конфигурация окружения живёт вне образа: `.env` не коммитится, обязательные переменные перечисляются в `.env.example`, секреты выдаются минимально необходимому контуру.
- Приложение обычно слушает внутренний порт, reverse proxy принимает публичный трафик, домен указывает на сервер, HTTPS завершает защищённое соединение. БД и панели мониторинга не публикуются без необходимости.
- Релиз воспроизводим: известны версия кода/образа, команды запуска, миграции, зависимости и критерии успешности. «На моём компьютере работает» не является проверкой сервера.
- Изменение схемы данных требует совместимости или плана миграции и отката. Не выполняй необратимую миграцию вместе с непроверенным кодом без страховки.

## Практический метод

1. Уточни цель: сервер, домен, ожидаемая нагрузка, ограничения, окно работ, допустимый простой, владелец DNS и секретов.
2. Проверь артефакты: чистый Git-статус, зафиксированная версия, Dockerfile/Compose, переменные, volumes, health endpoint, README и rollback-команды.
3. До релиза сними состояние и резервную копию постоянных данных. Проверь, что backup можно найти и есть понятный способ восстановления.
4. Выполни минимальный запуск и собери факты:

```bash
docker compose up -d --build
docker compose ps
docker compose logs app --tail=100
curl -f http://127.0.0.1:8000/health
```

5. Настрой или проверь reverse proxy, DNS и сертификат. Если прокси находится на том же сервере, публикуй порт приложения на `127.0.0.1`, а не на все интерфейсы.
6. Снаружи пройди ключевой пользовательский сценарий: открыть сайт, выполнить основное действие, прочитать сохранённые данные, проверить ошибку и мобильный экран.
7. Зафиксируй результат: версия, время, изменения, проверки, известные ограничения и точная процедура отката. После релиза наблюдай логи и основные метрики.

## Антипаттерны

- Выкатывать неизвестное состояние рабочей папки прямо на сервер.
- Считать `docker compose ps` достаточным подтверждением работоспособности.
- Хранить секреты в репозитории, образе, истории команд или скриншотах.
- Публиковать наружу БД, административные и monitoring-порты «для удобства».
- Исполнять `docker compose down -v`: флаг `-v` удаляет volumes и может уничтожить постоянные данные.
- Менять одновременно код, инфраструктуру, DNS и схему БД без промежуточных проверок.
- Обновлять продакшен без известной предыдущей версии и команды возврата.

## Критерии проверки

- Целевая версия и конфигурация однозначно идентифицируются; секреты не попали в Git.
- Все обязательные сервисы healthy/running, а логи не содержат циклических ошибок.
- Внутренний health-check и внешний HTTPS-адрес отвечают ожидаемо.
- Ключевой пользовательский сценарий проходит после релиза, включая запись и повторное чтение данных.
- Данные сохраняются после перезапуска контейнера; volumes и миграции проверены.
- Ненужные порты недоступны извне, сертификат валиден, ошибки не раскрывают внутренности.
- Есть проверенный либо операционно реалистичный rollback с владельцем и временем применения.
