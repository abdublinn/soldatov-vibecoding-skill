# Git и системы контроля версий

## Главная мысль

Git превращает быстро меняющийся AI-проект из хрупкой папки в управляемую историю. Коммит — проверенная точка, branch — изолированный эксперимент, diff — фактический отчёт о правке, revert/restore — разные способы отмены. Перед AI-изменением нужно знать текущее состояние и иметь путь назад.

## Модели и правила

- **Repository** — проект с историей; **working tree** — текущие файлы; **staging area** — выбранное содержимое следующего commit.
- `git status` отвечает «что изменено», `git diff` — «как именно», `git log --oneline --graph --decorate` — «какие точки уже существуют».
- Коммит фиксирует один смысловой и уже проверенный результат; сообщение объясняет изменение будущему читателю.
- Branch отделяет задачу от основной линии; merge переносит проверенный результат, conflict требует осознанного выбора.
- `git restore <file>` теряет незакоммиченные изменения файла; `git revert <commit>` безопасно отменяет опубликованный commit новым; `reset` переписывает положение истории и требует особой осторожности.
- Git не заменяет backup данных и секретов; `.gitignore` не удаляет уже отслеживаемый секрет из истории.

## Практический метод

Перед работой выполните `git status`; если есть чужие или незаконченные изменения, сначала разберите их. Зафиксируйте рабочую версию, затем создайте ветку: `git switch -c feature/status-filter`. Дайте AI одну задачу. После изменения выполните `git status` и `git diff`; проверьте запуск и сценарий; добавьте только нужные файлы через `git add <file>` и создайте понятный commit.

Если незакоммиченная правка плоха, сначала посмотрите `git diff <file>`, затем применяйте `git restore <file>` только осознанно. Для отмены уже общего commit предпочитайте `git revert <hash>`. Перед `pull`, сменой ветки и любой командой отката снова проверяйте `git status`.

## Антипаттерны

- Плодить `project_final_final_2` вместо истории Git.
- Выполнять `git add .` и commit, не просмотрев status/diff и секреты.
- Смешивать несколько задач и массовую AI-правку в одном commit.
- Использовать `reset --hard`, «очисти Git» или массовый restore без точного понимания потерь.
- Начинать новую AI-задачу поверх неизвестных незакоммиченных изменений.
- Коммитить сломанную промежуточную смесь как рабочую точку.

## Критерии проверки

- Перед правкой рабочее состояние известно и, если оно рабочее, зафиксировано.
- Для крупного/рискованного изменения создана отдельная ветка.
- Diff понятен: нет неожиданных файлов, секретов и несвязанных изменений.
- Проект запущен и главный сценарий проверен до commit.
- Commit содержит один смысловой результат и информативное сообщение.
- Выбранный способ отката соответствует состоянию: uncommitted, committed local или shared.
- После операции `git status` показывает ожидаемое состояние.
