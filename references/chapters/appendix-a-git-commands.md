# Краткий справочник команд Git

## Главная мысль

Команды Git полезны не как список для запоминания, а как безопасный язык управления состоянием проекта. Перед командой нужно понимать три зоны — рабочие файлы, индекс и история — и ожидаемый переход между ними. Базовый цикл `status → diff → add → diff --staged → commit` позволяет видеть, что именно будет сохранено. Команды восстановления, отмены и переписывания истории различаются по последствиям; при сомнении сначала используй читающие команды и создай точку возврата.

## Модели и правила

- `git status` показывает состояние; `git diff` — незастейдженные правки; `git diff --staged` — будущий commit; `git log` — историю. Это безопасная стартовая четвёрка.
- `git add` не «сохраняет навсегда», а помещает выбранные изменения в индекс. `git commit` создаёт именованную точку истории из индекса.
- Branch изолирует линию работы; switching безопасен только когда текущие изменения учтены. Название branch и сообщение commit должны объяснять намерение.
- `git restore <file>` отбрасывает незастейдженную правку файла; `git restore --staged <file>` убирает её из индекса, сохраняя в рабочей папке. Всегда сверяй вариант до запуска.
- `git revert <commit>` добавляет обратный commit и подходит для общей опубликованной истории. `git reset` двигает указатель истории и требует особой осторожности; `--hard` может уничтожить локальную работу.
- `.gitignore` предотвращает новое добавление локальных артефактов, но не удаляет уже отслеживаемый секрет из истории. Утёкший секрет нужно ротировать.

## Практический метод

Перед началом и перед любым commit выполни:

```bash
git status --short
git diff
git diff --staged
git log -5 --oneline
```

Создай отдельную ветку и маленький commit:

```bash
git switch -c feature/short-purpose
git add path/to/file
git diff --staged
git commit -m "Add observable outcome"
```

Для публикации сначала проверь remote и ветку: `git remote -v`, `git branch --show-current`, затем `git push -u origin <branch>`. Для получения изменений используй `git fetch` как безопасный обзор; после него сравни ветки и только затем выполняй merge/rebase по правилам проекта. Для отмены опубликованного изменения предпочитай `git revert <sha>`, проверь diff и тесты, затем публикуй обратный commit. Если нужно убрать файл из staged, не теряя правку: `git restore --staged path/to/file`.

## Антипаттерны

- Запускать `git add .` и commit, не просмотрев список файлов и staged diff.
- Коммитить `.env`, БД, сборки, логи, виртуальное окружение и токены.
- Использовать `git reset --hard`, `clean -fd` или force push как универсальное «исправление».
- Переключать ветки с непонятными локальными изменениями и конфликтами.
- Делать один commit на несколько несвязанных задач или маскировать логику массовым форматированием.
- Копировать команду AI без понимания, какие файлы/commits она изменяет и можно ли восстановиться.
- Считать удаление секретной строки последним commit достаточной реакцией на утечку.

## Критерии проверки

- До действия известны текущая ветка, статус и точный diff.
- В staged находятся только относящиеся к одной задаче файлы; секреты и локальные артефакты исключены.
- Commit имеет ясное сообщение и воспроизводимый результат; после него рабочее дерево ожидаемо чистое.
- Branch и remote выбраны явно; push не переписывает чужую историю.
- Отмена соответствует ситуации: restore для рабочей зоны, unstage для индекса, revert для опубликованной истории.
- Перед рискованной командой есть backup/branch/commit-точка и понятен путь возврата.
- После merge/revert выполнены тесты или ручная проверка целевого сценария.
