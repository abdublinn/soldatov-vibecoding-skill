# Мониторинг, логи и здоровье сервиса

## Главная мысль

Мониторинг нужен не ради красивой панели, а чтобы вовремя ответить на четыре вопроса: доступен ли сервис, что сломалось, насколько серьёзно влияние и нужно ли действовать сейчас. Минимальная наблюдаемость соединяет health-check, структурированные логи, системные и прикладные метрики и уведомления. Она проектируется от пользовательского сценария: зелёный CPU при неработающей форме не означает здоровый продукт. Сигналы должны помогать локализовать проблему и проверять результат исправления.

## Модели и правила

- **Лог** рассказывает о событии; **метрика** показывает динамику числа; **health-check** даёт быстрый статус зависимости; **alert** привлекает человека при значимом отклонении.
- Наблюдай три слоя: инфраструктура (CPU, RAM, диск, сеть), приложение (ошибки, latency, очередь, перезапуски) и продуктовый сценарий (успешные запросы, сохранение данных, критическая операция).
- Сначала минимальный набор сигналов, затем расширение по реальным сбоям. Сотни метрик без владельцев и порогов создают шум.
- Метрики без контекста сравнивай с базовой линией и временем события. Один пик не равен аварии; устойчивый рост ошибок вместе с жалобами — сильный сигнал.
- Monitoring-панели и collectors сами являются сервисами: им нужны ограничения ресурсов, постоянное хранение при необходимости и закрытые порты.
- Alert должен содержать объект, симптом, порог/время, ссылку на данные и первый безопасный шаг. У каждого важного alert есть владелец.

## Практический метод

1. Выпиши 3–5 критичных пользовательских действий и зависимостей каждого: приложение, БД, внешний API, диск, сеть.
2. Для каждого выбери проверяемый сигнал и порог. Например: доля 5xx, p95 времени ответа, число неуспешных сохранений, свободный диск, перезапуски контейнера.
3. Добавь простой `/health`; отдели «процесс жив» от «основные зависимости доступны», не раскрывая секретные детали.
4. Начни диагностику с запускаемых проверок:

```bash
docker compose ps
docker compose logs app --tail=100
curl -f http://127.0.0.1:8000/health
docker stats --no-stream
df -h
```

5. В минимальном стеке Prometheus собирает метрики, Grafana визуализирует, node exporter показывает хост, cAdvisor — контейнеры. Проверяй targets и datasource до настройки панелей.
6. Создай одну обзорную панель: доступность, ошибки, latency, нагрузка, память, диск, перезапуски. Добавь аннотации релизов, чтобы видеть связь изменения и симптома.
7. Проведи искусственную безопасную проверку уведомления и запиши runbook: что посмотреть, когда откатывать, кому эскалировать.

## Антипаттерны

- Устанавливать большой стек, не сформулировав решение, которое он поддерживает.
- Считать отсутствие алертов доказательством здоровья, если ключевой сценарий не измеряется.
- Логировать пароли, токены, персональные данные или полные тела запросов.
- Открывать Grafana, Prometheus, exporters и Docker API в публичный интернет без защиты.
- Перезапускать всё по первой красной метрике, теряя следы первопричины.
- Настраивать слишком чувствительные уведомления: постоянный шум учит команду игнорировать аварии.
- Хранить метрики бесконечно без политики retention и контроля диска.

## Критерии проверки

- Для каждого критичного сценария есть хотя бы один наблюдаемый сигнал и ответственный.
- Health-check отражает состояние нужных зависимостей и проверяется командой `curl`.
- Логи доступны, содержат время/уровень/контекст, но не содержат секретов и лишних персональных данных.
- Панель показывает ошибки, latency, ресурсы, диск и перезапуски; известна базовая линия.
- Monitoring targets имеют статус up, datasource работает, данные поступают с ожидаемым интервалом.
- Alert был тестово доставлен и ведёт к короткому runbook, а не только к графику.
- После релиза изменение сигналов можно связать с точной версией и использовать для решения об откате.
