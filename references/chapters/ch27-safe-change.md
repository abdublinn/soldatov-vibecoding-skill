# Как менять проект без разрушения

## Главная мысль

Чем ближе продукт к реальным пользователям и данным, тем важнее не скорость генерации, а управляемость изменения. Безопасная правка имеет узкую цель, ограниченную область, зафиксированное исходное состояние, критерии приёмки и путь возврата. AI полезен как анализатор и автор небольшого diff, но не должен самовольно «улучшать архитектуру» вокруг задачи. Документация решения и проверка после изменения превращают удачный эксперимент в воспроизводимую инженерную работу.

## Модели и правила

- Контур: **описать изменение → оценить влияние → создать точку возврата → внести минимальный diff → проверить цель и регрессии → документировать → выпустить/откатить**.
- Разделяй обязательное изменение, допустимые сопутствующие правки и явно запрещённые зоны. Если AI предлагает выйти за границы, остановись и пересмотри задачу.
- Делай отдельную branch или как минимум чистый commit до начала. Один commit должен выражать одну законченную мысль.
- Оценка влияния включает код, схему данных, API, UI, конфигурацию, секреты, зависимости, инфраструктуру и документацию.
- Для изменения данных нужен backup/миграция; для API — обратная совместимость; для инфраструктуры — порядок применения и rollback; для UI — проверка основных состояний.
- Решение фиксируй коротко: контекст, выбранный вариант, отвергнутые альтернативы и последствия. Это снижает повторное открытие уже закрытых вопросов.

## Практический метод

1. Сформулируй требование как наблюдаемый результат и acceptance criteria. Добавь `out of scope` и ограничения.
2. Проведи preflight:

```bash
git status --short
git diff
git log -1 --oneline
docker compose ps
```

3. Создай branch/commit-точку, проверь backup постоянных данных и запиши точную команду отката.
4. Попроси AI сначала перечислить затрагиваемые файлы, зависимости, риски и план проверки. Требуй минимальной реализации без несвязанных рефакторингов.
5. Просматривай diff по файлам. Не принимай скрытую смену библиотек, массовое форматирование, изменение схемы или удаление проверок как «побочный эффект».
6. Запусти узкие тесты, затем полный доступный набор. Пройди целевой сценарий, соседние функции, ошибки, роли и сохранность данных; проверь логи.
7. Зафиксируй изменение, обнови README/решение/инструкцию при необходимости. В production выпускай наблюдаемо; при нарушении критерия откатывай, а не наращивай непроверенные патчи.

## Антипаттерны

- Начинать правку в грязной рабочей директории, не понимая происхождение diff.
- Объединять исправление бага, обновление зависимостей и архитектурный рефакторинг.
- Разрешать AI менять «все связанные файлы» без списка и границ.
- Проводить необратимую миграцию без backup и проверенного плана восстановления.
- Проверять только новую кнопку, игнорируя роли, негативные ветки и существующие данные.
- Переписывать историю Git или использовать разрушительные команды ради удобного состояния.
- Продолжать латать production после ухудшения вместо возврата к известной рабочей версии.

## Критерии проверки

- Цель, acceptance criteria, out-of-scope и риски сформулированы до редактирования.
- Исходное состояние идентифицируется commit/version; рабочая область не содержит неучтённых изменений.
- Diff ограничен задачей, каждый затронутый файл объясним, секреты и данные не раскрыты.
- Есть рабочая точка возврата; для БД или файлов подтверждён backup/restore-контур.
- Узкие и регрессионные проверки проходят, целевой сценарий и ошибки ролей проверены.
- Логи/health/метрики после выпуска не показывают ухудшения; пользовательский эффект подтверждён.
- Документация и handoff отражают новое поведение, ограничения и способ отката.
