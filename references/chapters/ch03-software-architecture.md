# Базовая архитектура ПО простым языком

## Главная мысль

Архитектура — рабочая карта проекта: где интерфейс, логика, данные, API, конфигурация и эксплуатационные механизмы, как они связаны и где искать сбой. Новичку не нужна сложная теория, но без минимальной карты любая AI-правка превращается в ремонт проводки в темноте.

## Модели и правила

- **Четыре опоры:** frontend показывает и собирает действия; backend применяет правила; database хранит состояние; API задаёт договор обмена между частями.
- **Поддерживающие контуры:** файловое хранилище, уведомления, аналитика, логирование и админка — отдельные механизмы, каждый добавляется только ради сценария.
- **Authentication ≠ authorization.** Первое подтверждает, кто вошёл; второе проверяет, что этому субъекту разрешено сделать. Роль — удобная группа прав, но backend должен реально проверять действие.
- **Биллинг — контур состояний.** Оплата включает тарифы, статусы, лимиты, ошибки, возвраты и webhooks, а не одну кнопку.
- **Устойчивость — часть архитектуры.** Логи, health-check, backup и мониторинг нужны для ответа «что произошло» и восстановления, а не для солидности.

## Практический метод

Составьте архитектурную карту до генерации: пользовательские роли; frontend-экраны; backend-действия; API-маршруты; сущности и база; внешние сервисы; env-переменные; файлы/volumes; логи и health-check. Затем проведите по карте главный сценарий и одну ошибку. Для создания заявки: форма → POST API → валидация → сохранение → ответ → список менеджера → лог события.

Просите AI сначала назвать компоненты и связи, затем объяснить каждое решение через сценарий и MVP. Отдельно перечислите упрощения: например, в учебной версии нет регистрации, но доступ к списку предполагается только во внутреннем контуре. Упрощение должно быть видимым ограничением, а не тайной дырой.

## Антипаттерны

- «Выбери лучшую архитектуру сам» без пользователей, нагрузки, данных и условий сопровождения.
- Смешивать frontend, backend и database в одну магическую «админку».
- Добавлять storage, email, аналитику, биллинг или роли «на будущее» без сценария.
- Полагаться только на frontend-проверку прав или валидации.
- Хранить данные внутри контейнера и считать их постоянными.
- Называть backup существующим, не проверив восстановление; считать «container running» здоровьем сервиса.

## Критерии проверки

- Для каждого видимого действия известны backend-обработчик, данные и ответ.
- API-договор содержит вход, успешный результат и основные ошибки.
- Ясно, где находятся постоянные данные и что переживает перезапуск или пересоздание.
- Права проверяются на серверной стороне для критических операций.
- Секреты поступают через env, а публичные порты и внешние сервисы перечислены.
- Есть место, где увидеть ошибку, и простой health-check; backup имеет владельца и процедуру восстановления.
- Карту может прочитать другой человек и локализовать frontend-, backend-, database- или network-проблему.
