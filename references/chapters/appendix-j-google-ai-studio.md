# Google AI Studio: подробный гайд для новичка

Снимок книги 2026 года: перед применением сверить текущую официальную документацию.

## Главная мысль

Google AI Studio позволяет быстро проверить prompt/model и собрать AI-приложение, но эксперимент в интерфейсе, общий доступ к прототипу и production-развёртывание — разные уровни готовности. Основная задача — сохранить воспроизводимый prompt/код, привязать ресурсы к правильному Cloud Project, не раскрыть API key и осознанно перенести выполнение на production-контур с IAM, квотами, billing и наблюдаемостью. Модели, названия вкладок, лимиты и способы deploy меняются быстрее методики.

## Модели и правила

- Playground/прототипирование проверяет поведение модели и параметры; Build создаёт приложение/код; Cloud Project определяет ключи, квоты, billing и ответственность.
- Share предоставляет доступ к артефакту в рамках текущих возможностей сервиса; Deploy создаёт эксплуатационный ресурс. Ни один не равен автоматически безопасной production-поставке.
- API key — секрет. Он не должен попадать в browser bundle, опубликованный prompt, repository или screenshot. Клиент обращается к backend, а backend — к модели.
- Для production предпочтителен управляемый identity-контур (например, service account/IAM в соответствующем сервисе), минимальные роли, отдельные dev/prod projects и контролируемый billing.
- Prompt, system instruction, параметры модели, схема ответа, тестовые примеры и версия модели — часть воспроизводимого артефакта.
- Качество AI проверяется набором сценариев и границ, а не одним удачным ответом. Отдельно тестируются ошибки, quota, timeout, unsafe input и недоступность модели.

## Практический метод

1. Опиши задачу и evaluation set: нормальные, пограничные и запрещённые входы; ожидаемый формат, критерии полезности и допустимый отказ.
2. В Playground сравни prompts/параметры на одном наборе. Сохрани выбранную конфигурацию и причины, не ориентируйся на самый эффектный единичный ответ.
3. В Build создай минимальный end-to-end сценарий. Просмотри сгенерированный код, зависимости, сетевые вызовы и место использования key.
4. Экспортируй код через доступный механизм (ZIP/GitHub) и проверь локальный/чистый запуск. Перенеси секрет в server-side env, добавь `.env.example` без значения.
5. Проверь Cloud Project: владелец, billing, quotas, API, dev/prod разделение, IAM. Для production выбери текущий официально поддерживаемый контур и identity.
6. Добавь timeout, retry с ограничением, обработку quota, валидацию структуры ответа, логирование без чувствительных prompts и метрики стоимости/ошибок.
7. Разверни, пройди evaluation set и внешний пользовательский сценарий; настрой бюджетные уведомления, мониторинг и rollback версии prompt/model/code.

## Антипаттерны

- Считать удачный ответ в Playground доказательством стабильного продукта.
- Публиковать API key во frontend или вместе с shared/exported проектом.
- Смешивать dev и production в одном ключе/проекте без лимитов и владельца billing.
- Зависеть от незафиксированного имени/версии модели и предполагать неизменность ответа.
- Передавать модели персональные/закрытые данные без правового и технического решения.
- Делать бесконечные retries при quota/ошибке, увеличивая стоимость и нагрузку.
- Путать Share с production deploy или оставлять артефакт доступным шире необходимого.

## Критерии проверки

- Prompt/model/parameters/schema и evaluation set сохранены и воспроизводимы.
- Код экспортирован и понятен; browser не получает ключ или server credentials.
- Cloud Project, billing, quotas, API и owners настроены для нужной среды; роли минимальны.
- Нормальные, пограничные, unsafe и failure-сценарии дают контролируемый результат.
- Timeout/retry/валидация/логи/метрики предотвращают тихие сбои и бесконтрольные расходы.
- Published/deployed приложение проходит внешний сценарий; известны версия и rollback.
- Текущие возможности, цены и лимиты сверены по официальной документации на дату применения.
