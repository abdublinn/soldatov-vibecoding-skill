# Первый учебный проект: генерация, запуск и правки

## Главная мысль

Первая генерация — каркас, а не результат. Ценность появляется после фактической установки, запуска, карты файлов, ручного прохождения главного сценария, серии малых проверяемых правок и фиксации рабочей версии в Git. До этого «готово» означает лишь правдоподобный набор файлов.

## Модели и правила

- **Первая итерация:** предкодовый пакет → prompt → структура → код → локальный запуск → checks → малые правки → commit.
- Сначала оцените соответствие brief и отсутствие лишнего, затем исправляйте запуск; не добавляйте новые функции.
- README — инструкция-кандидат: команды подтверждаются терминалом, фактическая команда заменяет выдуманную.
- **Недоделка ≠ bug.** Не реализованная out-of-scope функция не ошибка; сломанный заявленный сценарий — ошибка.
- Один change затрагивает ограниченную цепочку и получает собственную проверку.
- Рабочая версия фиксируется только после smoke-test и проверки секретов/локальных артефактов.

## Практический метод

После генерации сначала просмотрите дерево и список расхождений с ТЗ. Выполните установку строго из files/README; сохраните полный текст первой ошибки. Найдите entry point, model, form, list/card, CSS, JS, config и storage. Пройдите сценарий: создать заявку → увидеть в списке → открыть → изменить статус → обновить страницу/перезапустить app → убедиться в сохранении.

Затем сделайте пять маленьких правок по одной: текст кнопки; backend-validation; правило статуса; HTML-поле/состояние; CSS-улучшение. Перед каждой назовите файлы и acceptance step, после — запустите сценарий и просмотрите diff. Перед первой фиксацией выполните `git status`, исключите `.env`, `.venv`, caches и ненужную локальную базу; обновите README фактической командой; создайте смысловой commit.

## Антипаттерны

- Сразу просить улучшения, роли или дизайн до первого успешного запуска.
- Применять пять AI-патчей подряд и тестировать только в конце.
- Лечить локальную ошибку переписыванием архитектуры.
- Считать открывшуюся главную страницу доказательством CRUD и persistence.
- Коммитить секреты, virtual environment, build artifacts или неизвестные файлы.
- Оставлять README с неверной командой, потому что «у меня и так запускается».

## Критерии проверки

- Структура проекта сопоставлена с предкодовым пакетом, лишнее отмечено.
- Зависимости устанавливаются, фактическая команда запуска записана.
- Главная страница открывается, но приёмка идёт по полному пользовательскому сценарию.
- Validation видна человеку; данные переживают требуемый update/restart.
- Для каждого малого change понятны затронутые файлы и проверка.
- `git diff` не содержит неожиданных переделок, а status — чувствительных/временных файлов.
- Первый commit обозначает реально работающую и воспроизводимую версию, known issues записаны отдельно.
