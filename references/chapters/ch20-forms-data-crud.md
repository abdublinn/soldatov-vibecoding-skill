# Формы, данные и CRUD-логика

## Главная мысль

Форма — не набор полей, а договор между UI, validation, backend и моделью данных. CRUD описывает жизненный цикл сущности: создать, прочитать список/деталь, изменить, удалить или безопасно архивировать. Если поле не проходит всю цепочку и не переживает ожидаемый перезапуск, функция остаётся декорацией.

## Модели и правила

- **Сначала сущность, затем форма.** Поля имеют тип, обязательность, источник, правила и владельца.
- **Create / Read / Update / Delete** переводятся в пользовательские сценарии, маршруты, права и условия успеха.
- Validation нужна на UI для удобства и обязательно на backend для надёжности.
- **Статус — состояние процесса, не цветной badge.** Переходы имеют правила, роли и запрещённые направления.
- Физическое delete часто опаснее архива/`closed`; выбор должен соответствовать бизнес-смыслу и handoff.
- Изменение data model требует карты влияния и, для постоянной базы, migration/совместимости данных.

## Практический метод

Составьте CRUD-карту: операция; роль; экран; endpoint/handler; validation; storage; success/error. Для заявки отдельно проверьте create с корректными и пустыми данными, read списка и детали, update статуса/комментария, запрос несуществующего id. Если delete не нужен в MVP, запишите это явно и используйте закрытие/архивирование.

Перед добавлением поля `phone` найдите model/schema, migration, HTML `name`, JS payload, backend-validation, persistence, response и отображение. После правки создайте запись, перечитайте её через отдельный запрос/страницу, обновите, перезапустите app и проверьте сохранение. Для статусов сделайте таблицу `from → to → role → condition → error`; backend должен отклонять недопустимый переход.

## Антипаттерны

- Добавить поле только в форму или только в модель.
- Хранить данные в памяти и обещать persistence.
- Полагаться на `required` в HTML без server validation.
- Разрешить любой переход статуса или проверять права только в UI.
- Удалять запись физически без подтверждения, владельца и бизнес-необходимости.
- Просить «полноценный production CRUD», получая роли, audit log и сложность вне MVP.

## Критерии проверки

- Сущность и каждое поле имеют смысл, тип, обязательность и источник.
- Create отклоняет плохие данные и создаёт ровно одну корректную запись.
- List/detail показывают фактические данные и корректно обрабатывают пустой список/unknown id.
- Update сохраняется и виден после перечитывания/перезапуска.
- Недопустимый status transition или неавторизованная роль получает контролируемую ошибку.
- Delete/архивирование соответствует зафиксированному правилу и не уничтожает данные случайно.
- Data-model change имеет migration/compatibility plan и проверку старых данных.
