# Рабочее окружение вайбкодера

## Главная мысль

Окружение — часть продукта: папка проекта, редактор, терминал, версии runtime, зависимости, env, база и команда запуска. Если запуск нельзя повторить, хороший код остаётся локальным фокусом. Порядок в окружении отделяет ошибку реализации от неправильной команды, отсутствующей зависимости или случайной настройки.

## Модели и правила

- **Одна папка — один актуальный проект.** Копии `final_2` не заменяют Git и создают неопределённость для человека и AI.
- **Зависимости декларативны.** Python-пакеты фиксируются в `requirements.txt`/`pyproject.toml`, JavaScript — в `package.json` и lockfile; ручная установка не является передачей проекта.
- **Изоляция окружения.** `.venv` отделяет Python-зависимости проекта; контейнер — более широкий способ зафиксировать runtime.
- **Конфигурация отделена от кода.** `.env` хранит локальные реальные значения и игнорируется Git; `.env.example` перечисляет имена и безопасные примеры.
- **README — исполняемая память.** Команды в нём нужно проверять в чистой сессии.
- Backend, frontend, docs и конфигурация лежат предсказуемо; временные файлы исключены.

## Практический метод

До генерации создайте корень проекта, Git, `README.md`, `.gitignore`, `.env.example`, каталоги `backend/`, `frontend/` и `docs/` только если они действительно нужны. Проверьте runtime-командами вроде `python --version`, `node --version`, затем создайте изолированное окружение и установите зависимости из файла.

Запишите фактический маршрут запуска: текущая директория → активация окружения → установка → подготовка env → инициализация данных → команда сервера → ожидаемый URL/порт → место логов. Попросите AI провести аудит структуры, но не удалять дубли и не переносить файлы автоматически: сначала получить карту, назначение и риски. После изменения зависимостей обновляйте декларативный файл, а не только текущую машину.

## Антипаттерны

- Хранить `app_old.py`, `app_fixed.py`, `project-final-2/` рядом без источника истины.
- Исправлять `ModuleNotFoundError` ручной установкой на сервере, не обновляя зависимости проекта.
- Коммитить `.env`, `.venv`, `node_modules`, caches или локальную базу без осознанной причины.
- Использовать глобальные версии runtime и не указывать поддерживаемую версию.
- Давать README с непроверенной командой, сгенерированной для другого стека.
- Смешивать ключи, заметки и выгрузки клиента в корне репозитория.

## Критерии проверки

- У проекта одна понятная корневая папка и Git-репозиторий.
- Runtime и зависимости устанавливаются из явных файлов.
- Реальный `.env` исключён, `.env.example` полон и не содержит секретов.
- Backend/frontend/docs отделены только там, где это отражает архитектуру.
- Команда запуска воспроизводится в новой shell-сессии и открывает ожидаемый порт.
- README содержит подготовку, запуск, проверку, ограничения и место логов.
- После паузы другой человек может отличить код, конфиг, данные и временные артефакты.
