# UML: зачем нужны диаграммы и как они помогают вайбкодеру

## Главная мысль

Диаграмма нужна не ради формальной нотации, а чтобы сделать решения видимыми: кто действует, какие данные существуют, как проходит запрос, из чего состоит система и где она развёрнута. Сначала смысл, потом строгость обозначений; одна диаграмма отвечает на один вопрос.

## Модели и правила

- **Use Case Diagram** отвечает «кто что делает»: акторы и доступные им действия внутри границы системы.
- **Activity Diagram** показывает поток шагов, решения, ветвления и завершения пользовательского или внутреннего процесса.
- **Sequence Diagram** раскрывает порядок сообщений между участниками: пользователь → frontend → backend → database, включая ошибочную ветку.
- **Class Diagram** в beginner-режиме фиксирует сущности, основные поля и связи, а не демонстрирует всю объектную теорию.
- **Component Diagram** показывает крупные части и их зависимости; **Deployment Diagram** — где эти части работают: браузер, сервер, контейнер, база, внешний сервис.
- Роли, сущности, процессы и компоненты нельзя смешивать в одну схему без ясного вопроса.

## Практический метод

Выберите решение, которое нужно принять. Для прав доступа нарисуйте Use Case; для пути заявки — Activity или Sequence; для модели данных — Class; для состава проекта — Component; для выкладки — Deployment. Ограничьте схему MVP и используйте одинаковые названия с requirements и кодом.

Дайте AI brief и запросите текстовую/PlantUML/Mermaid-заготовку конкретного типа. Например: «Sequence для создания заявки: user, frontend, backend API, database; добавь ветку validation error; не добавляй функции вне MVP». Затем вручную проверьте каждый узел и стрелку: существует ли этот участник, что передаётся, что происходит при отказе. Схема становится контекстом для следующей задачи, а не декоративным приложением.

## Антипаттерны

- «Нарисуй полную UML всей системы» — обычно смешивает несколько вопросов в нечитаемую карту.
- Считать красивую схему доказательством правильной архитектуры.
- Добавлять компоненты и роли, которых нет в brief, потому что «так принято».
- Рисовать последовательность только для счастливого пути, пропуская валидацию и сбой.
- Использовать разные названия одной сущности в схеме, требованиях и коде.
- Сохранять диаграмму после изменения системы, не обновляя её.

## Критерии проверки

- У диаграммы есть один сформулированный вопрос и подходящий тип UML.
- Акторы не смешаны с сущностями, компоненты — с действиями, deployment — с логикой процесса.
- Граница системы и внешние участники различимы.
- Для sequence/activity отражена хотя бы главная ошибочная или альтернативная ветка.
- Сущности и связи совпадают с текущим MVP и моделью данных.
- Каждый элемент можно объяснить через требование или проверочный сценарий.
- После диаграммы стало понятно, какое решение принять или какую задачу дать AI.
