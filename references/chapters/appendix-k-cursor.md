# Cursor IDE: подробный гайд для вайбкодера

Снимок книги 2026 года: перед применением сверить текущую официальную документацию.

## Главная мысль

Cursor эффективен, когда AI работает внутри понятного репозитория с ограниченным контекстом, а человек управляет планом, diff, командами и историей. IDE не превращает ответ модели в проверенный код: Agent может неверно понять границы, затронуть лишние файлы или выполнить рискованную команду. Начинай с карты проекта и режима планирования, затем разрешай малые изменения, просматривай diff и запускай проверки. Правила, skills, hooks и дополнительные agents полезны как повторяемые guardrails, но их конкретный интерфейс меняется.

## Модели и правила

- Контекст определяет качество: открытый файл, выделение, явно упомянутые paths, правила проекта и найденные символы лучше, чем весь repository без цели.
- Plan/Ask используется для исследования и решения; Agent/Edit — для согласованной реализации. Для незнакомой или рискованной задачи сначала запрети изменения.
- Diff — обязательная точка контроля. Accept/reject выполняй по файлам и логическим блокам, не принимай пакет только потому, что тест запустился.
- Git остаётся системой возврата: чистый status, отдельная branch, маленькие commits и review защищают от длинной AI-итерации.
- Project rules фиксируют устойчивые соглашения; skill описывает повторяемый workflow; hook может проверять/ограничивать действие; subagent уместен для изолированного анализа. Не прячь важные требования только в чате.
- Terminal-команда имеет те же права, что пользователь. Перед разрешением оцени цель, cwd, файлы, сеть, секреты и обратимость.

## Практический метод

1. Открой правильный root и прочитай README, инструкции/правила и текущий status. Попроси Cursor составить карту entrypoints, data flow, tests и unknowns без правок.
2. Опиши задачу: expected/actual, scope/out-of-scope, затрагиваемые слои, acceptance, запрещённые файлы и rollback.
3. В Plan попроси перечень файлов, шаги и проверки. Согласуй один маленький этап; создай branch/commit-точку.
4. Разреши Agent выполнить этап. Просмотри каждый diff: логика, несвязанные изменения, зависимости, secrets, migrations, удаление тестов и массовое форматирование.
5. Запусти узкие проверки, затем полный набор и пользовательский сценарий. Ошибку возвращай с полным логом; не разрешай циклические случайные fixes.
6. Закрепи устойчивые conventions в актуальном механизме rules/skills; hooks используй для format/test/secret checks, но проверяй их фактическое выполнение.
7. Сделай ясный commit, обнови docs и подготовь handoff: что изменено, почему, как проверить, риски и следующий шаг.

## Антипаттерны

- Открывать родительскую папку с несколькими проектами и давать Agent широкую команду.
- Просить «исправь приложение» без воспроизведения, scope и acceptance.
- Автоматически принимать все diffs или разрешать terminal-команды без чтения.
- Передавать `.env`, production logs с токенами или реальные персональные данные в prompt.
- Позволять Agent обновить все зависимости и рефакторить архитектуру ради локального бага.
- Считать rules/hooks гарантией безопасности без проверки конфигурации и результата.
- Продолжать длинную сессию после потери контекста вместо нового краткого handoff.

## Критерии проверки

- Открыт точный project root; карта и инструкции прочитаны до изменения.
- Plan перечисляет минимальный scope, файлы, риски, тесты и rollback.
- До Agent есть чистое/понятное Git-состояние и точка возврата.
- Каждый diff просмотрен; лишние файлы, секреты, массовые изменения и скрытые migrations отсутствуют.
- Запущены узкие/полные проверки и реальный сценарий; логи после правки ожидаемы.
- Rules/skills/hooks содержат только устойчивые правила и фактически применяются.
- Commit и handoff позволяют другому человеку понять и повторить результат без истории чата.
