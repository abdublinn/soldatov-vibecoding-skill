# Replit IDE: подробный гайд для вайбкодера

Снимок книги 2026 года: перед применением сверить текущую официальную документацию.

## Главная мысль

Replit объединяет постановку задачи, AI-генерацию, код, preview, окружение и публикацию, поэтому быстро сокращает путь от идеи к работающему URL. Та же связность создаёт риск спутать красивый preview с готовым продуктом и потерять контроль над кодом, данными, секретами или стоимостью. Работай артефактами: сначала brief/план, затем маленькая генерация, просмотр файлов и checkpoints, проверка сценария, настройка production-секретов и только после этого Publish. Названия режимов, лимиты и тарифы могли измениться.

## Модели и правила

- Режим планирования нужен для вопросов, архитектуры и этапов; режим построения — для изменения проекта; облегчённый режим подходит только ограниченным задачам. Проверяй, разрешены ли сейчас изменения.
- Workspace/code — источник истины; Preview показывает запущенный результат; Canvas/визуальный редактор ускоряет UI-правки, но не заменяет просмотр diff и логики.
- Checkpoint/история даёт точку возврата к файлам проекта. Отдельно выясняй судьбу БД, внешних данных и секретов: rollback кода может не откатывать данные.
- Development и deployment — разные окружения. Secrets, домен, команда запуска, build, storage и масштабирование для production проверяются отдельно.
- Публикация выбирается под режим приложения: статический контент, долгоживущий web-сервис или другой поддерживаемый тип. Не выбирай deployment только по минимальной цене.
- GitHub нужен для независимой истории и handoff; синхронизация не отменяет контроля branch, secrets и конфликтов.

## Практический метод

1. До Agent создай brief: пользователь, ценность, один сценарий, MVP/out-of-scope, данные, роли, критерии и ограничения расходов.
2. Попроси план без генерации. Проверь предложенный стек, структуру, внешние сервисы и вопросы; сократи первый этап до end-to-end vertical slice.
3. Перед каждой значимой итерацией создай/проверь checkpoint. Разрешай Agent менять ограниченный scope, после ответа просмотри список файлов и diff/code.
4. Запусти Preview и пройди loading/empty/success/error, сохранение и повторное чтение, перезапуск и мобильный экран. Ошибку передавай AI с логом и воспроизведением.
5. Раздели development secrets и production secrets; ключи не помещай в prompt или frontend. Проверь storage и резервирование данных.
6. Перед Publish уточни тип deployment, build/run, домен, HTTPS, health, лимиты/стоимость и rollback. Пройди внешний smoke по опубликованному URL.
7. Подключи/экспортируй GitHub, обнови README и `.env.example`; передай owners репозитория, deployment, billing и домена.

## Антипаттерны

- Начинать с длинного «сделай весь SaaS» и принимать первый preview как результат.
- Позволять Agent переписывать проект без checkpoint и просмотра затронутых файлов.
- Считать визуальную правку в Canvas безопасной для состояний, данных и адаптивности.
- Вставлять API keys в чат, код клиента или публичный Repl.
- Предполагать, что rollback checkpoint восстанавливает внешнюю/production БД.
- Нажимать Publish без понимания выбранного deployment, лимитов, сна и постоянного storage.
- Оставлять production и billing на личном аккаунте автора без handoff.

## Критерии проверки

- План согласован до генерации, первый scope мал и имеет acceptance criteria.
- Известны изменённые файлы и checkpoint; откат кода проверяем, границы отката данных задокументированы.
- Preview проходит основной и негативные сценарии; данные сохраняются ожидаемым способом.
- Secrets разделены по средам и отсутствуют в коде/Git/чатах.
- Published URL работает снаружи по HTTPS, health/logs доступны, домен и стоимость контролируются.
- Тип deployment соответствует приложению; restart/scale не уничтожают постоянные данные.
- GitHub/README/env/handoff позволяют владельцу продолжить работу вне текущей сессии.
