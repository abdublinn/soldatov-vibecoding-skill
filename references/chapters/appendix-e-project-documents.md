# Шаблоны документов проекта

## Главная мысль

Документы проекта — не бюрократический комплект, а внешняя память для решений, проверки и передачи. Каждый артефакт должен отвечать на конкретный вопрос и иметь владельца: brief — зачем и для кого, требования — что должно наблюдаться, архитектура — из чего и как связано, README — как запустить, runbook — как эксплуатировать, decision record — почему выбран вариант, handoff — что получает следующий владелец. Документ ценен лишь пока соответствует работающей системе.

## Модели и правила

- Минимальный набор до кода: product brief, пользовательские сценарии, границы MVP, данные/статусы, acceptance criteria, схема компонентов и список рисков.
- Минимальный набор для репозитория: README, `.env.example`, инструкции setup/run/test, структура каталогов, зависимости и способ проверить основной сценарий.
- Для production добавляются deploy/rollback, backup/restore, monitoring/runbook, роли/доступы, security notes, ограничения и владельцы внешних сервисов.
- Короткий ADR фиксирует контекст, решение, альтернативы и последствия. Он нужен там, где будущий участник иначе снова откроет спор.
- Документируй интерфейсы и инварианты, а не переписывай каждую строку кода. Ссылки на source of truth лучше копий, которые расходятся.
- Обновление документа входит в Definition of Done изменения. Если инструкция не проверена на чистом окружении, она является гипотезой.

## Практический метод

1. Создай product brief: проблема, пользователь, сценарий сейчас/после, ценность, ограничения, метрика успеха, MVP и out-of-scope.
2. Оформи требования таблицей: идентификатор, условие/действие/результат, приоритет, acceptance, зависимость. Для данных добавь сущности, поля, статусы и правила переходов.
3. Сделай архитектурную страницу: контекст, компоненты, поток запроса/данных, внешние сервисы, trust boundaries и ключевые решения.
4. README строй как путь нового участника: назначение → требования → setup → env → run → test → типовые ошибки → ссылки на эксплуатацию.
5. В deploy/runbook опиши preflight, backup, команды, health/smoke, monitoring, инцидент, rollback. Используй копируемые команды с явными placeholders.
6. Перед handoff добавь inventory доступов без самих секретов, owners, известные ограничения, backlog и критерии приёмки.
7. Проверь комплект ролью нового владельца: разверни на чистом окружении только по тексту, отметь разрывы и обнови source of truth.

## Антипаттерны

- Создавать длинную спецификацию, которую никто не связывает с acceptance и кодом.
- Копировать одни и те же настройки в README, wiki и инструкции с разными значениями.
- Вставлять реальные пароли и токены в шаблоны, примеры или screenshots.
- Описывать только happy path, пропуская ошибки, роли, миграции и rollback.
- Фиксировать решение без причины и отвергнутых альтернатив.
- Передавать диаграмму, не соответствующую текущим сервисам и потокам.
- Считать автоматически сгенерированный AI-текст готовой документацией без фактического прогона.

## Критерии проверки

- Каждый документ отвечает на определённый вопрос, имеет владельца и актуальную дату/версию.
- Brief, MVP и acceptance согласованы: функция не существует только в одном из артефактов.
- README позволяет новому участнику запустить и проверить продукт в чистом окружении.
- Архитектура отражает фактические компоненты, данные, внешние зависимости и границы доверия.
- Deploy/runbook содержит backup, health/smoke, monitoring и rollback с запускаемыми командами.
- Секретов нет; `.env.example` и inventory описывают лишь имена, назначение и владельцев.
- Handoff явно перечисляет ограничения, backlog и доступы, а получатель подтвердил самостоятельную проверку.
