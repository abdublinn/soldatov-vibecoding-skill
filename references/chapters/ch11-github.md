# GitHub как рабочая площадка проекта

## Главная мысль

GitHub — не облачная папка, а поверхность доверия и передачи проекта. Репозиторий должен показать, что это за продукт, как его запустить и проверить, что входит в MVP, какие ограничения и риски известны, где задачи и как менялась система. Код без этой упаковки остаётся зависимым от памяти автора.

## Модели и правила

- **Git** хранит локальную историю; **remote** связывает её с сервером; `push` отправляет, `pull` получает и объединяет изменения.
- **README — входная дверь.** Он описывает ценность, MVP, стек, запуск, env, ручную проверку, ограничения и следующий шаг.
- **`.env.example` показывает форму конфигурации без секретов**, `.gitignore` исключает локальные и чувствительные файлы.
- **Issues** фиксируют проблему, шаги воспроизведения, ожидаемое поведение и acceptance criteria; это не склад неясных пожеланий.
- Публичность — решение о риске: private для чувствительных материалов и незрелого проекта; public только после проверки истории, лицензии и данных.
- Репозиторий — часть handoff: новый человек должен воспроизвести запуск без голосовой инструкции.

## Практический метод

Соберите предсказуемую структуру: `README.md`, `.gitignore`, `.env.example`, код, `docs/` со схемами и handoff-заметками. Проверьте локальную историю, создайте remote, отправьте ветку и откройте репозиторий как получатель. В README начните с проблемы и главного сценария; затем укажите фактические команды установки/запуска, переменные без значений, ручной smoke-test и честный список out of scope.

Для каждой известной ошибки заведите issue только если есть симптом, контекст, шаги и критерий закрытия. Попросите AI проверить README глазами человека, который впервые получил код, но потребуйте ссылаться на реальные файлы и не выдумывать функции или команды.

## Антипаттерны

- Отправлять ссылку на репозиторий без README и считать проект переданным.
- Публиковать `.env`, токены, локальную базу, клиентские данные или внутренние документы.
- Писать README по намерениям, а не по фактически проверенному запуску.
- Использовать один commit «final» с хаотичной историей и непонятными изменениями.
- Делать public «для портфолио», не проверив лицензию, секреты и персональные данные.
- Описывать issue как «починить всё» без воспроизведения и приемки.

## Критерии проверки

- Репозиторий имеет понятное имя, описание и актуальный README.
- Чистый получатель может установить зависимости и запустить проект по инструкции.
- `.env.example` перечисляет нужные ключи, а реальные секреты отсутствуют во всей публикуемой истории.
- Главный сценарий проверяется по конкретным шагам README.
- MVP, ограничения, known issues и следующие шаги различены.
- Коммиты объясняют смысл изменений; issues воспроизводимы и проверяемы.
- Выбранная видимость соответствует чувствительности проекта и материалов.
